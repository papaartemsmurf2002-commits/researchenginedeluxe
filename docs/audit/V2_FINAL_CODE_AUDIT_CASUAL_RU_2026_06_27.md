## Коротко

Проект не выглядит сломанным. Главная проблема не в том, что “ещё не найдена идеальная стратегия”. Цель проекта как раз и есть быстро искать, убивать плохие идеи и оставлять только то, что проходит жёсткие тесты.

Реальные проблемы сейчас такие:

1. Движок может быть намного быстрее на твоём железе.
2. Некоторые проверки результата слабее, чем твои реальные правила.
3. Математика комиссий/ликвидности должна знать размер аккаунта в долларах.
4. Большие данные местами превращаются в Python-словари, хотя должны идти через быстрые колоночные таблицы.
5. Новые биржи стоит добавлять осторожно как источники проверки, а не как повод раздувать архив ради архива.

## Что не является проблемой

### 700 GB данных не в Git — это нормально

Их не надо коммитить. Для этого и существует `.gitignore`. Большой локальный архив — нормальная часть такого проекта.

### Старые документы говорят “не готово”, новые говорят “готово” — это нормально

Это просто этапы разработки. Не надо чинить старые исторические документы только потому, что проект продвинулся дальше.

### Нет прибыльной OI/L2/funding стратегии — это не баг репозитория

Репозиторий должен дать инфраструктуру, которая честно проверяет стратегии. Сам факт, что какая-то семья стратегий пока не дала результат, не значит, что проект плохой.

### Hyperliquid старые 1m свечи через public API не надо бесконечно добивать

Публичный Hyperliquid candleSnapshot ограничен недавними свечами. Для старой истории нужны другие честные источники или прокси-данные с нормальной пометкой происхождения.

## Твоё железо меняет вывод

У тебя сильная локальная машина:

- Ryzen 7 7700, 16 потоков, около 5.3 GHz.
- RTX 5070 Ti.
- 64 GB DDR5 6400.
- Очень быстрые NVMe SSD.

Значит проблема не в компьютере. Проблема в том, что код местами работает как “много маленьких Python-объектов”, а не как быстрый массив/таблица.

Проще:

```text
Железо может быстро гонять миллионы строк.
Но если каждая строка становится dict/object в Python, скорость убивается.
```

Лучший путь:

1. Сначала ускорить CPU/Arrow/Polars/NumPy.
2. Потом, если надо, подключать GPU.
3. Не строить облачную/распределённую систему раньше времени.

## Самые важные правки

### 1. Добавить размер аккаунта в расчёт ликвидности

Сейчас участие в объёме считается примерно как:

```text
turnover / volume
```

Но `turnover` — это вес портфеля, например 0.05, а volume может быть долларовым объёмом бара. Без размера аккаунта это не честная проверка ликвидности.

Нужно:

```text
trade_notional_usd = вес_сделки * account_notional_usd
participation_rate = trade_notional_usd / volume_notional_usd
```

Почему важно: стратегия может выглядеть ликвидной на “виртуальном $1 аккаунте”, но умереть на реальном размере капитала.

### 2. Жёстко проверять 10 сделок в месяц

Сейчас в ledger есть проверка типа “сделок больше 0”. Это слишком слабо.

Нужно правило:

```text
trade_count / usable_months >= 10
```

Если меньше — стратегия не проходит accepted research.

### 3. Проверять не больше 2 убыточных месяцев в год

Нужно считать месячные доходности и блокировать результат, если в любом 12-месячном окне больше 2 убыточных месяцев.

Иначе может пройти стратегия, которая заработала на одном хорошем куске и была плохой большую часть времени.

### 4. Один `full_window` fold не должен доказывать стабильность

Сейчас возможно, что один общий период называется fold и даёт stability score 1.0. Это не нормальная проверка устойчивости.

Нужно:

```text
accepted research требует минимум 4-6 walk-forward fold'ов
```

Один `full_window` можно оставлять для диагностики, но не для финального accepted результата.

### 5. Ускорить backtest engine

Сейчас “vectorized” движок на деле всё ещё много делает через Python loops и dict/object строки.

Нужно два движка:

```text
reference_engine_python — медленный, но простой и проверочный
fast_vectorized_engine — быстрый на массивах
```

Быстрый вариант должен работать так:

```text
таблица данных -> массивы time x instrument x field
сигналы -> матрица
веса -> матрица
доходности -> матрица
turnover -> матрица
комиссии -> векторно
```

Ожидаемый выигрыш: в больших прогонах может быть 10x-100x.

### 6. Не прогонять backtest заново для stress costs

Сейчас stress_2x и stress_3x могут заново гонять всю симуляцию. Это лишняя работа.

Правильно:

```text
один раз посчитать сигналы, веса, turnover, returns
потом пересчитать только комиссии/slippage/impact для stress сценариев
```

Это сразу даёт примерно 2x-3x ускорение для каждого полного прогона.

### 7. Не читать Parquet в Python dict до фильтрации

Сейчас сервис backtest-data читает Parquet, превращает строки в Python dict, потом фильтрует по времени.

Нужно наоборот:

```text
сначала фильтр на уровне Arrow/Polars:
ts >= start AND ts < end AND instrument_id IN (...)
потом уже, если надо, маленький результат превращать в Python
```

Твои SSD очень быстрые, но если код превращает всё в Python-объекты слишком рано, SSD не спасает.

### 8. Ledger и manifest не должны полностью переписываться на каждую новую запись

Сейчас местами логика такая: прочитать весь parquet ledger, добавить строку, записать весь ledger заново.

На тысячах прогонов это станет тупо медленно.

Лучше:

```text
ledger/parts/ledger_part_000001.parquet
ledger/parts/ledger_part_000002.parquet
ledger/append_log.jsonl
ledger/compacted/current.parquet
```

Писать кусками, иногда compact.

### 9. Worker store надо чуть укрепить для параллельных воркеров

SQLite WAL — нормальный выбор. Но claim job лучше делать атомарно, чтобы два воркера точно не схватили одну работу при гонке.

Также надо чистить не только `RUNNING` stale jobs, но и `CLAIMED`, если воркер умер между claim и start.

### 10. Spread должен иметь понятные единицы

Сейчас `spread` может быть понят как fraction, bps или абсолютная разница цены. Это опасно.

Нужно разделить:

```text
spread_abs
spread_bps
spread_fraction
```

И не угадывать единицы по размеру числа.

## Маленькие баги, которые легко поправить

### funding 0.0 bug

Если funding равен `0.0`, код может принять это за false и взять `funding_rate` вместо настоящего нуля.

Нужно явно проверять `is not None`.

### aggTrades length check

В одном старом парсере Binance aggTrades проверяется, что строка имеет минимум 6 элементов, но потом читается 7-й элемент. Надо заменить проверку на 7 или использовать новый payload parser.

### usable months лучше считать точнее

Сейчас месяцы считаются грубо по разнице календарных месяцев. Для accepted research лучше явно определить: нужны полные месяцы или достаточно дней.

## Что делать с биржами

### Binance

Самый полезный bulk источник. Его стоит держать главным для больших архивов: klines, aggTrades, trades, bookDepth, bookTicker и т.д.

### Hyperliquid

Хорош для:

- текущего universe/meta;
- funding history с pagination;
- L2 snapshot;
- recent candles.

Не надо пытаться через public candleSnapshot вытащить старую 2024 intraday историю, если API это не даёт.

### Bybit

Хороший второй источник. Есть kline, OI, funding. Но OI/funding надо нормально пагинировать и доказать отдельными тестами, прежде чем считать coverage-ready.

### OKX

Оставить как probe lane, пока не проверена нормальная история и pagination.

### Bitget

Стоит добавить как следующий probe источник. У него есть history candles, но лимиты маленькие: до 90 дней диапазон и до 200 строк. Это не “bulk archive”, а нормальный secondary/probe источник.

### MEXC / Gate

Можно добавить позже как availability probes, но не раньше, чем ускорен движок и ужесточена валидация.

## Правильный порядок работ

### Шаг 1. Усилить validation

Добавить:

```text
>= 10 trades/month
<= 2 losing months/year
fold_count >= 4/6
full_window_only не проходит accepted research
```

Это сразу уменьшит мусорные “прошедшие” стратегии.

### Шаг 2. Исправить cost/capacity math

Добавить:

```text
account_notional_usd
trade_notional_usd
participation_rate через dollar volume
явные spread units
```

Это делает результат ближе к реальности.

### Шаг 3. Сделать быстрый engine

Оставить старый Python engine как reference, но добавить быстрый массивный engine.

### Шаг 4. Сделать быстрый data loader

Arrow/Polars фильтрация до Python.

### Шаг 5. Переписать ledger/manifest append на parts

Не переписывать весь Parquet на каждую запись.

### Шаг 6. Ускорить OF materialization

Process pool + Parquet output + cache by raw_sha/version.

### Шаг 7. Добавить venue probes

Сначала Bitget и Bybit OI/funding pagination, потом OKX/MEXC/Gate.

## Главное финальное мнение

Проект выглядит как нормальная исследовательская система, а не как “дырявый трейдинг-бот”. Самое полезное сейчас — не спорить о старых статусах и не собирать ещё бесконечные данные, а сделать так, чтобы каждая проверка стратегии была:

```text
быстрой
жёсткой
понятной по математике
честной по источникам данных
```

Если это сделать, твоя локальная машина должна тянуть очень много итераций без облака и без лишнего усложнения.
