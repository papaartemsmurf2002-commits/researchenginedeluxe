BTC/ETH HYBRID TRADING FRAMEWORK - VERIFIED BLUEPRINT
Date: 2026-04-09
Status: Research-verified and crosschecked draft for implementation

1. Objective

Build a production-ready hybrid trading system where:

- TradingView provides the entry signal on 15m bars.
- A Python service validates, sizes, executes, and exits trades.
- Hyperliquid is the execution venue.
- Binance perpetual futures data is used for historical bars and, if desired, microstructure confirmation.

This document keeps the parts of the original blueprint that are well-supported, corrects the parts that are mislabeled or overstated, and filters out lower-priority complexity for later phases.


1.1 Implementation phase map

To keep implementation priorities explicit, use the following phase split:

- V1:
  - BTC execution and safety core.
  - TradingView-compatible ingress, manual fallback ingress, Binance reference data, Hyperliquid execution, persistence, reconciliation, and triple-barrier supervision.
- V2:
  - Main BTC TradingView-to-acceptance phase.
  - Includes TradingView-facing BTC work needed to complete the acceptance layer, including signal acquisition, provenance handling, BTC signal-history bootstrapping, BTC dataset/research integration around TradingView-origin signals, and operator workflows needed to inspect and validate that path.
  - Keeps focus on BTC only while finishing the research-backed acceptance loop, advanced BTC exits, and promotion-readiness monitoring.
- V3:
  - Expansion phase after BTC V2 is stable.
  - Main objectives are the ETH layer, a cleaner GUI/operator layer for safe tweaking, and an extensive suite of tuning and research instruments.
  - TradingView does not begin in V3; V3 broadens the already-established BTC TradingView path into a larger multi-asset and operator-facing system.


2. Executive Conclusion

The overall architecture is viable, but five important corrections are needed before implementation:

- Triple-barrier exits are strong and should stay, but the exact 30-candle timeout is a strategy hyperparameter, not a universal research result.
- The proposed "OFI" formula in the original note is not canonical OFI. "Market buy volume minus market sell volume" is signed trade imbalance, not full order flow imbalance.
- A fixed Hurst threshold such as H > 0.55 is not research-validated as a universal cutoff for BTC/ETH intraday trading. It must be calibrated out-of-sample.
- Binance can serve as the primary market-data and microstructure venue for BTC/ETH perps even when execution happens on Hyperliquid, but live basis and execution-quality monitoring must remain first-class controls.
- "Beta-adjusted ETH sizing" as defined by sigma_BTC / sigma_ETH is actually volatility scaling, not beta adjustment.

Bottom line:

- KEEP: Python manager, event-driven state machine, Binance-primary market data, ATR-based price barriers, vertical time barrier, duplicate-signal lock, flip logic, SQLite/event-log persistence, Hyperliquid execution.
- KEEP WITH MODIFICATION: Hurst regime feature, OFI-style microstructure features, probability-calibrated acceptance model, adverse-selection and alpha-decay exits.
- DEFER BEYOND V2: ETH expansion, ETH-specific cross-asset architecture, cleaner GUI/tuning workbench expansion, and complex cross-asset beta models.
- KEEP IN V2: BTC TradingView signal handling, BTC signal-history bootstrapping, BTC dataset/research integration, BTC acceptance modeling, and advanced BTC exit supervision.
- OPTIONAL LATER V2 OR POST-V2: HMM regime layer once the simpler BTC acceptance stack is already proven.


3. What Holds Up Under Research Review

3.1 Triple barrier method

This is the strongest part of the blueprint.

- Lopez de Prado's triple-barrier framework is well-established for path-dependent labeling and can be adapted sensibly for live trade management.
- The key idea is sound for live exits: use an upper barrier, lower barrier, and vertical time barrier, then exit when the first one is hit.
- For your holding horizon of roughly 1.5 to 3.75 hours, a time-based exit is especially useful because stale trades often decay in edge even if they never hit a hard stop.

Implementation conclusion:

- Use ATR-scaled take-profit and stop-loss levels captured at entry time.
- Add a hard vertical barrier in elapsed candles or elapsed wall-clock time.
- Use Hyperliquid native reduce-only TP/SL trigger orders as a failsafe, but keep the vertical barrier in Python because it is strategy-specific.


3.2 Order flow imbalance as a short-horizon confirmation signal

The microstructure literature strongly supports order flow imbalance as predictive for short-horizon price pressure.

- Cont, Kukanov, and Stoikov show that short-interval price changes are strongly linked to imbalance between supply and demand at the best bid and ask.
- The relationship is more robust than raw trade volume alone.

Important correction:

- Canonical OFI is built from order-book events and queue changes at the best bid/ask, including limit order arrivals, cancellations, and marketable trades.
- "Market buy volume minus market sell volume" is a simpler signed taker-flow metric. It is useful, but it should be named trade imbalance or signed taker imbalance, not OFI.

Implementation conclusion:

- V1 should use signed taker imbalance because it is simpler and easier to validate.
- V2 can add true OFI by reconstructing a local order book from Binance diff-depth plus REST snapshot, or by using Hyperliquid l2Book for same-venue pressure.


3.3 Hurst exponent as a regime feature

Hurst-based regime filtering is directionally reasonable, but much weaker as a hard rule than the original note implies.

- H > 0.5 is commonly interpreted as persistence, H around 0.5 as random-walk-like behavior, and H < 0.5 as anti-persistence.
- However, modern research also warns that classical R/S and related estimators can be biased in finite samples and unreliable with heavy-tailed financial returns.
- Lo's modified R/S results are an important warning against over-interpreting apparent long memory in returns.
- Recent crypto/fractal studies do find persistent behavior in Bitcoin and related series, but the effect size can be modest at intraday horizons.

Implementation conclusion:

- KEEP Hurst as a slow regime feature, not a binary truth machine.
- Do not assume H > 0.55 is a universal threshold.
- Estimate H on a slower rolling 15m window, not on very short microstructure windows.
- Calibrate the threshold strictly out-of-sample and compare against a no-Hurst baseline.


3.4 Hidden Markov models for regimes

HMMs are legitimate tools for market regime detection and have been applied to crypto regime-switching research.

However:

- They add modeling, training, retraining, and monitoring complexity.
- They are not necessary to get the first live version working.
- They are much harder to validate than the simpler gates in your current design.

Implementation conclusion:

- HMM is valid, but not high priority.
- Treat it as a phase-2 overlay only after the simpler filters are proven.


3.5 Volatility-normalized ETH sizing

Normalizing ETH position size relative to BTC volatility is sensible as risk control.

Important correction:

- PositionSize_ETH = Target * (sigma_BTC / sigma_ETH) is volatility scaling, not beta adjustment.
- True beta adjustment would involve covariance with BTC (or a market proxy), not just the ratio of standard deviations.

Implementation conclusion:

- KEEP the concept.
- Rename it to volatility normalization or inverse-vol scaling.
- Only introduce rolling beta if you later prove it improves out-of-sample stability.


4. Critical Corrections To The Original Blueprint

4.1 OFI wording correction

Original idea:
"Market Buy Vol - Market Sell Vol" over the last 15-60 seconds.

Corrected interpretation:

- This is signed taker imbalance.
- It is acceptable for V1.
- It should not be called OFI unless you are rebuilding the book and tracking queue updates.


4.2 Hurst threshold correction

Original idea:
"Only enter if H > 0.55; reject if H < 0.52."

Corrected interpretation:

- The 0.55 and 0.52 values are heuristics, not universal constants.
- Research does not justify hard-coding them without walk-forward evidence.
- Crypto intraday H values can cluster close to 0.5, so small threshold changes can have large selection effects.

Recommended stance:

- Search the threshold on validation windows only.
- Start with a broad sweep such as 0.50, 0.52, 0.54, 0.56.
- If the effect disappears out-of-sample, remove the filter.


4.3 Vertical barrier correction

Original idea:
"Research shows stale trades lose their edge, so hard exit at 30 candles."

Corrected interpretation:

- The idea of a vertical barrier is supported.
- The exact 30-candle setting is not directly research-proven for your strategy.
- The timeout must be learned from your own distribution of trade decay.

Recommended stance:

- Test 12, 18, 24, and 30 candles out-of-sample.
- Use MAE/MFE decay and expectancy by holding-time bucket to choose the timeout.


4.4 Venue mismatch correction

Original idea:
Use Binance microstructure to validate signals, then execute on Hyperliquid.

Corrected interpretation:

- For BTC and ETH perps, using Binance as the primary reference venue is defensible.
- Hyperliquid's official oracle and mark-price documentation show that external CEX prices are directly embedded in its fair-value process, with Binance carrying the highest weight among the listed CEX inputs.
- This does not make the two venues identical, but it materially reduces the concern that Binance is a poor reference source for BTC/ETH execution on Hyperliquid.

Recommended stance:

- Use Binance futures as the historical and reference venue if TradingView entries are based on Binance perps.
- It is acceptable to use Binance microstructure as the primary signal and filter venue for BTC/ETH.
- Keep a live basis monitor between Binance reference price and Hyperliquid fill/mark price so the assumption remains measured rather than assumed.
- Hyperliquid trades or l2Book can still be useful as a secondary execution-health check, but they are not mandatory for the core design.


4.5 "Beta-adjustment" correction

Original idea:
Scale ETH by sigma_BTC / sigma_ETH and call it beta-adjusted.

Corrected interpretation:

- This is volatility scaling, not beta adjustment.
- In crypto, rolling beta estimates can be unstable and noisy.

Recommended stance:

- Start with inverse-vol scaling only.
- Revisit beta only if you later add portfolio-level exposure control.


5. Recommended Production V1

5.1 Components

A. Webhook gateway
- FastAPI or Flask endpoint.
- Receives TradingView payload.
- Enforces authentication and request signature.
- Generates a unique signal_id.

B. Market data service
- Binance USD-M futures REST and websocket as the primary historical and live market-data layer for BTC.
- Binance REST endpoints for funding, premium, open interest, and open-interest history.
- Hyperliquid websocket and user streams for execution-state, fills, funding, and reconciliation.

C. Feature engine
- ATR on 15m bars.
- Rolling Hurst on 15m bars.
- Signed taker imbalance over short recent windows.
- Top-of-book imbalance and queue imbalance from synced depth.
- Premium, funding, open-interest, and realized-volatility features.

D. Acceptance layer
- Consumes the feature packet and outputs accept/reject, confidence bucket, and size multiplier.
- Uses calibrated probabilities and explicit model/calibration versioning.

E. Risk and position manager
- Tracks current position, side, entry timestamp, entry ATR, barrier levels, and outstanding order ids.
- Enforces one active position per symbol.
- Handles duplicate same-direction signals and flips.

F. Execution adapter
- Hyperliquid order placement and cancellation.
- Uses client order ids.
- Uses reduce-only trigger orders for stop and take-profit where possible.
- Uses Python-managed time barrier.
- Must support three execution modes on the same code path:
  - `shadow`: emit intended actions only, no exchange orders
  - `paper`: simulated position and fill model
  - `live`: real exchange orders

G. Persistence
- SQLite is acceptable for a single-process bot.
- Use WAL mode and transactional updates.
- Keep both current state and append-only event log.
- Persist human-readable decision and action logs for every signal and trade state transition.


5.2 Recommended live flow

On webhook receipt:

1. Validate payload and deduplicate by signal_id plus bar timestamp.
2. Pull latest 15m bar state and recompute ATR and Hurst.
3. Pull live microstructure confirmation:
   - Primary V1: Binance aggTrade signed taker imbalance plus top-of-book imbalance.
   - Secondary execution-health checks: Hyperliquid user/order state, fills, and optional l2Book/bbo.
4. Compute the feature packet and apply hard risk vetoes plus the current acceptance threshold.
5. If same-direction position already exists, ignore signal.
6. If opposite-direction position exists:
   - Cancel resting exits.
   - Close current position.
   - Confirm close via order update or fill event.
   - Open new position.
7. After entry fill:
   - Store entry price, ATR, Hurst, imbalance stats, signal id, model version, calibration version, and barrier timestamps.
   - Place reduce-only TP and SL trigger orders if supported in desired grouping.
   - Start time-barrier supervision in Python.
8. During trade:
   - Monitor fill state, time barrier, and exchange disconnects.
   - Reconcile local state with Hyperliquid user events on reconnect.
9. On exit:
   - Cancel stale resting orders.
   - Persist PnL, exit reason, and latency stats.

In `shadow` mode:

- The system should print and persist a readable action ticket instead of placing orders.
- Each ticket should include:
  - timestamp
  - symbol
  - proposed side
  - accept/reject decision
  - acceptance probability and confidence bucket
  - feature highlights that drove the decision
  - intended size
  - intended entry method
  - intended TP, SL, and time barrier
  - reason for hold, reject, reduce, flip, or exit


6. Recommended Baseline Features And Hard-Filter Baselines For V1

6.1 Regime feature

Use Hurst as a soft gate or meta-model input:

- Compute on rolling 15m closes or returns.
- Use a sufficiently long window such as 256 to 512 bars.
- Treat it as a persistence score, not a precise market-state oracle.

Pass rule candidates to test:

- H > 0.50
- H > 0.52
- H > rolling median of H
- H z-score above threshold relative to trailing history

The last two are often more stable than fixed constants.


6.2 Microstructure feature

Preferred V1:

- Signed taker imbalance over 10s, 20s, 30s, and 60s windows.
- Long signal requires positive imbalance above threshold.
- Short signal requires negative imbalance below threshold.

Possible threshold forms:

- Raw signed size
- Signed notional
- Z-score relative to recent short-window history
- Percentile filter, for example only top/bottom 20 percent of pressure readings

Recommended use:

- Use these thresholds first as a simple hard-filter baseline for ablation.
- If the meta-labeled acceptance model outperforms the hard-filter baseline, promote the features into the model and keep only risk vetoes as hard blocks.

Do not start with full multi-level OFI unless the simpler version already improves out-of-sample results.


6.3 Exit logic

Recommended V1 exit stack:

- Profit barrier: entry +/- k_tp * ATR_entry
- Stop barrier: entry -/+ k_sl * ATR_entry
- Time barrier: fixed maximum holding time

Important implementation note:

- Freeze ATR at entry for the initial research build. This avoids moving the target after trade entry and makes backtests cleaner.
- Later, if desired, test trailing or adaptive variants separately.

10. Testing And Validation Requirements

10.1 Research hygiene

- Keep the TradingView KNN training period separate from filter tuning.
- Tune the Python filters and acceptance layer only on data the KNN never saw.
- Use walk-forward or expanding-window evaluation.

10.2 Required ablation ladder

Measure performance in this order:

- Entry model only
- Entry + triple-barrier only
- Entry + simple hard microstructure filters
- Entry + meta-label acceptance model
- Entry + calibrated probability thresholding
- Entry + meta-label + adverse-selection exit
- Entry + meta-label + full exit hierarchy
- ETH-specific risk normalization only after BTC stack is locked

Only keep a layer if it improves out-of-sample performance after costs.

10.3 Metrics that matter

- Net expectancy after fees and slippage
- Profit factor
- Median and mean holding time
- MAE and MFE by trade
- Rejection rate by filter
- Flip frequency
- PnL by exit reason
- Latency from webhook receipt to order submission
- Venue basis between Binance reference and Hyperliquid fill

10.4 Latency target

The original "<= 500 ms" target is reasonable for this strategy, but not mission-critical in the HFT sense.

Practical target:

- Under normal conditions, validate and submit within 250 ms to 750 ms.
- Prioritize determinism, reconnect safety, and idempotency over shaving a few milliseconds.

14. Advanced Research Addendum - BTC/ETH Perps Only

14.1 Main conclusion from this second research pass

For the stated objective, the strongest architecture is not "more hard filters."

The strongest architecture is:

- Keep the TradingView model as the directional engine.
- Use research-backed features to build a secondary acceptance model that decides whether to act on each proposed trade.
- Reserve hard filters only for risk and market-integrity vetoes.

This matters because too many hard gates usually destroy recall and flatten the original model's edge. Meta-labeling is the cleaner framework when the objective is to filter model outputs without compromising their core information content.


14.2 Best-fit filtering framework: meta-labeling over the primary entry model

Research-backed interpretation:

- Lopez de Prado's meta-labeling framework is directly aligned with your problem.
- The primary model decides side.
- A secondary model predicts whether the primary bet is worth taking.
- Triple-barrier outcomes are the natural supervisory labels for this secondary model.

Practical conclusion:

- Do not hand-build a large boolean rule stack as the final acceptance logic.
- Instead, compute a rich feature vector at signal time and let a secondary model estimate:
  - probability the trade should be accepted
  - probability TP is hit before SL
  - expected value proxy or confidence score
- Use that score for accept/reject and optionally for position sizing.

Recommended hard vetoes only:

- stale or missing Binance data
- webhook duplication or replay
- exchange/API desync
- spread/depth abnormality beyond tolerance
- funding or basis abnormality beyond tolerance
- maximum concurrent risk reached

Everything else should preferably be a feature, not a hard rule.


14.3 Highest-value feature groups for BTC/ETH perp entry filtering

14.3.1 Microstructure features

These are the highest-priority live features.

- Signed taker imbalance from Binance `aggTrade` over 10s, 20s, 30s, and 60s windows.
- Top-of-book imbalance and queue imbalance from synced Binance diff-depth data.
- Spread, best-level depth, and short-horizon depth depletion.
- Trade burst metrics:
  - aggressive trade count
  - aggressive notional
  - imbalance z-score relative to recent history

Research interpretation:

- OFI and queue imbalance explain short-horizon price pressure well.
- Multi-level OFI can improve explanatory power further, but is more complex.
- Cross-asset OFI research shows that lagged cross-impact exists but decays quickly.

Implementation priority:

- V1 feature set: signed taker imbalance + top-level book imbalance.
- V2 feature set: integrated multi-level OFI.


14.3.2 Perpetual-specific context features

These are important because the strategy trades perps, not spot.

- Current funding rate.
- Funding-rate change.
- Time to next funding event.
- Premium/basis versus reference price or oracle.
- Open interest level.
- Open interest change.

Recommended use:

- Use funding and OI first as features, not hard blocks.
- Promote them to hard vetoes only if testing shows that extreme values reliably destroy expectancy.

Operational note:

- Binance and Hyperliquid have different funding mechanics, so record both venue contexts where relevant.
- On Hyperliquid, funding is paid hourly and is derived from an 8-hour rate formula sampled continuously.


14.3.3 Regime and volatility features

These features complement the microstructure layer and help avoid taking good-looking signals in bad market states.

- Hurst exponent as a slow persistence feature.
- Realized volatility percentile.
- ATR percentile.
- Realized upside/downside semivariance split.
- Jump or shock flag based on realized-volatility discontinuity or large-bar z-score.
- Session and time-of-day features.

Research interpretation:

- Crypto markets exhibit intraday periodicity tied to major global trading sessions.
- BTC and ETH returns are heavy-tailed and strongly heteroskedastic, so volatility-state awareness is not optional.
- Hurst is useful as a regime input, but not strong enough to be a universal veto by itself.


14.3.4 Cross-asset BTC/ETH features

For a BTC/ETH-only system, this is one of the most important upgrades.

- Shared market-mode factor from BTC and ETH realized volatility.
- Relative-strength spread or return differential between BTC and ETH.
- BTC microstructure context as a feature for ETH entries.
- BTC volatility state as a feature for ETH entries.
- ETH state as contextual input for BTC entries, but with lower expected importance.

Research interpretation:

- Cross-asset impact exists at short horizons and decays rapidly.
- External crypto volatility information improves volatility forecasting.
- BTC and ETH should not be forced into a single parameter set.

Implementation conclusion:

- Train separate acceptance models for BTC and ETH.
- Allow ETH model features to depend more heavily on BTC state than vice versa.
- Do not assume a fixed BTC-leads-ETH trading rule unless it survives out-of-sample testing.
- Treat this whole BTC/ETH cross-asset block as V3 work, not as a blocker for completing BTC V2.


14.4 Advanced entry-filter design recommendation

Recommended architecture:

Primary layer:
- TradingView KNN decides Long or Short.

Secondary layer:
- Python acceptance model decides:
  - accept or reject
  - confidence bucket
  - size multiplier

Suggested secondary-model candidates:

- logistic regression for baseline interpretability
- gradient-boosted trees for nonlinear interactions
- calibrated probability output for thresholding

Recommended output use:

- Accept only when probability/confidence exceeds a symbol-specific threshold.
- Map confidence to size using a capped schedule.
- Keep a fixed maximum risk budget regardless of confidence.
- Calibrate probabilities before using them for thresholding or sizing.

Most important principle:

- Let the secondary model combine features nonlinearly.
- Avoid replacing it with a manually tuned "all filters must agree" rule set unless the simpler baseline clearly wins out-of-sample.


14.5 Sophisticated exit engine recommendation

The strongest exit engine for this framework is hierarchical, not single-rule.

Layer 0: Exchange-native protection
- On fill, place reduce-only protective stop and take-profit orders on Hyperliquid wherever contract/order semantics allow.
- These are fail-safe exits, not the full strategy.

Layer 1: Base triple barrier
- Entry-time stop barrier using ATR or forecast volatility.
- Entry-time profit barrier using ATR or forecast volatility.
- Vertical barrier using elapsed bars or elapsed wall-clock time.

Layer 2: Adverse-selection exit
- If post-entry microstructure flips sharply against the position within the first short holding window, and the trade has not achieved minimum favorable excursion, exit early.
- This is the most valuable extension beyond vanilla triple barrier.

Suggested trigger inputs:

- signed taker imbalance reversal
- queue imbalance reversal
- spread/depth deterioration
- aggressive opposite-side burst

Layer 3: Alpha-decay exit
- Recompute the acceptance score every new 15m bar or on shorter internal cadence.
- If the score collapses below the minimum viability threshold, flatten or reduce.
- This handles "trade is not wrong enough to stop out, but edge has decayed."

Layer 4: Volatility-shock adjustment
- If volatility regime expands sharply after entry, reduce the remaining time budget and tighten supervision.
- If a large discontinuity/jump is detected against the trade, do not wait passively for the original time barrier.

Layer 5: Funding-aware cleanup
- Near funding timestamps, do not carry mediocre or decayed trades through funding if the expected carry is adverse.
- Funding should not dominate the strategy, but it should be part of exit hygiene.

Layer 6: Optional trailing-profit logic
- After the trade reaches a meaningful favorable excursion, trail using a volatility-based stop or locked-in-fraction rule.
- This is a tactical add-on and should be tested only after the earlier layers are stable.


14.6 What should be dynamic and what should stay fixed

Keep fixed at entry:

- initial stop multiple
- initial profit multiple
- baseline time barrier
- max risk budget

Allow to update during trade:

- adverse-selection status
- acceptance-score decay
- volatility-shock status
- funding proximity logic
- optional trailing stop once trade is sufficiently in profit

This split keeps the system interpretable while still allowing sophisticated trade supervision.


14.7 BTC-versus-ETH implementation guidance

Do not treat BTC and ETH as the same market with different volatility.

Recommended rule:

- Separate model weights.
- Separate filter thresholds.
- Separate exit calibration.
- Shared global risk controls.

BTC:

- Use Binance microstructure and perp context as the main decision inputs.
- Cross-asset ETH context is optional and should remain secondary.

ETH:

- Use ETH microstructure, but include BTC regime and BTC microstructure context as first-class features.
- Keep volatility normalization mandatory.
- Expect the acceptance layer to matter more than for BTC.

Important implication:

- "One filter stack for both coins" is unlikely to be optimal.
- "One architecture with separate BTC and ETH calibration" is the correct design target.
- BTC should be the entire focus of early and mid-stage iterations.
- ETH is the last priority and should be added only after the BTC framework is stable; this includes deferring ETH work even beyond optional HMM experimentation on BTC.


14.8 Validation protocol for the advanced setup

To keep the filtering layer from overfitting the base model:

- Label trades using triple-barrier outcomes.
- Train the acceptance model only on signals generated by the primary model.
- Use purged walk-forward evaluation because trade labels overlap in time.
- Use a final locked out-of-sample period for decision-making.
- Track Deflated Sharpe Ratio and Probability of Backtest Overfitting when selecting among filter stacks.

Required comparison ladder:

- Primary model only
- Primary + simple hard filters
- Primary + meta-label acceptance model
- Primary + meta-label + adverse-selection exit
- Primary + meta-label + full exit hierarchy

Keep a layer only if it improves:

- net expectancy after costs
- drawdown control
- stability across BTC regimes and time periods
- out-of-sample precision of accepted trades

Critical guardrail:

- A filter that improves win rate by destroying too many good trades is not an improvement.
- Optimize for economic value added, not cosmetic accuracy.


14.9 Strongest research-backed recommendation

If only one major addition is implemented next, it should be this:

- Build a meta-labeled acceptance model on top of the TradingView directional signal using:
  - Binance microstructure
  - BTC/ETH cross-asset state
  - perp funding/OI context
  - volatility and regime features
  - triple-barrier outcomes as labels

If only one major exit upgrade is implemented next, it should be this:

- Add adverse-selection and alpha-decay exits on top of the existing triple-barrier engine.

Those two additions are the most likely to improve trade selection quality without flattening the original model edge.

Priority note:

- All major research, tuning, and implementation iterations should focus on BTC first.
- ETH should not be part of the initial optimization loop.
- BTC TradingView signal acquisition, BTC provenance handling, BTC signal-history bootstrapping, and BTC dataset/research integration remain part of V2.
- ETH expansion is a V3 objective after the BTC TradingView-to-acceptance loop is stable and validated.


14.10 Tandem design principle: entry filter and exit engine should share the same state language

The acceptance layer and exit layer should not be designed as independent silos.

Recommended tandem design:

- At entry time, persist a full decision packet:
  - raw market snapshot
  - derived features
  - model version
  - calibration version
  - acceptance probability
  - confidence bucket
  - regime label
  - chosen barriers and time budget
- The exit engine should consume this packet as the initial trade context.
- During trade management, only state updates available after entry should modify supervision.

This creates a coherent live loop:

- entry model proposes direction
- acceptance model scores whether the trade is worth taking
- execution engine places and reconciles orders
- exit engine supervises the trade using entry context plus post-entry state updates
- research engine later replays the exact same packet for attribution and retraining

Recommended research hypothesis to test:

- lower-confidence accepted trades should have tighter adverse-selection tolerance and shorter time budgets
- higher-confidence accepted trades can retain the full base barrier profile

This should be treated as a testable design, not a prior assumption.


14.11 V3 main objectives

Once BTC V2 is stable, V3 should focus on three expansions:

- ETH layer:
  - ETH-specific acceptance model.
  - ETH-specific risk normalization and barrier tuning.
  - ETH-versus-BTC feature separation.
  - Cross-asset BTC context for ETH only where it survives out-of-sample testing.
- Clean GUI/operator layer:
  - easier operator workflows
  - safer parameter visibility and tweaking surfaces
  - cleaner research, metrics, and artifact navigation
  - clearer testing and review visibility without terminal-style noise
- Extensive tuning and research instruments:
  - richer replay comparison tooling
  - threshold and calibration diagnostics
  - parameter sweep workflows
  - session and regime breakdowns
  - artifact and version comparison tooling

Important V3 rule:

- The GUI and tuning suite must remain a thin layer over the canonical backend and must never become a separate strategy implementation path.


15. Final Production Architecture Recommendation

15.1 Preferred system shape

The best architecture for this project is a modular async monolith with an event-driven internal design, not a distributed microservice system.

Why:

- It is sophisticated enough for low-latency trading logic.
- It avoids unnecessary operational complexity.
- It keeps research, replay, and live execution on the same code path.

Recommended internal modules:

- ingress gateway
- Binance market-data adapters
- feature engine
- acceptance-model inference service
- risk and portfolio manager
- Hyperliquid execution adapter
- reconciliation engine
- exit supervisor
- telemetry and drift monitor
- research/replay engine


15.2 Non-negotiable implementation rules

- Use the same feature code for historical research, replay, paper trading, and live inference.
- Persist every decision as an append-only event plus normalized feature snapshot.
- Make all order-placement actions idempotent via signal ids and client order ids.
- Reconcile local state against Hyperliquid user streams and periodic state snapshots.
- Fail closed on stale data, heartbeat loss, or unresolved position ambiguity.


15.3 Runtime controls required for live safety

- feed staleness monitor for Binance trades, depth, and bars
- websocket heartbeat/ping handling for Hyperliquid connections
- order acknowledgment timeout
- fill reconciliation timeout
- Binance-versus-Hyperliquid basis monitor
- spread/depth abnormality circuit breaker
- max daily loss and max open-risk kill switch
- automatic transition to safe mode on reconnect uncertainty

These controls are part of the strategy, not just infrastructure.


15.4 Monitoring that should exist from day one

Decision-quality monitoring:

- acceptance rate
- PnL by confidence bucket
- TP-before-SL rate by score decile
- calibration drift between predicted probability and realized outcome
- rejection reason distribution

Execution-quality monitoring:

- latency from webhook to order submission
- latency from order submission to first acknowledgment
- slippage versus Binance mid and Binance mark
- slippage versus Hyperliquid mid and fill
- cancel/reject rate
- basis at entry and exit

System-health monitoring:

- websocket reconnect count
- sequence-gap count for depth sync
- state-reconciliation mismatch count
- missed-heartbeat count


15.5 Deployment protocol

- Start in full shadow mode with live data and no real orders.
- Move to paper-trade or smallest-possible capital deployment.
- Promote only after score calibration, slippage, and reconciliation metrics are stable.
- Freeze model and threshold versions during each evaluation window.
- Retrain only on a scheduled research cycle, not ad hoc during live stress.

Shadow-mode requirement:

- Shadow mode must be fully readable by a human operator.
- Every intended trade action should be visible in terminal logs and persisted in structured form.
- The operator should be able to compare:
  - raw signal
  - acceptance decision
  - intended order plan
  - eventual hypothetical exit path
  - realized market movement after the decision
- This mode is the primary environment for testing, tuning, and trust-building before live API execution.


15.6 Final implementation guidance

For best odds of a strong live system, the project should be built around one principle:

- every research result must survive the exact same feature computation, decision logging, and replay path that the live system uses

That is the most important architectural safeguard against silent overfit, training-serving skew, and false confidence in backtests.
